# Session 10 (2026-09-06) — dX TC64 kernel K-slice 16 → 32

## Hypothesis

The dX TC64 kernel (`gemm_backward_dx_tc.cu`) is sync/latency-bound in its
16-deep WMMA loop: every 16 reduction rows it does one load-sync-mma-sync
cycle (64×16 dY + 16×64 W per sync). Sessions 7–8 showed update's *same
pattern* is not DRAM-bound — the cost is the sync chain. The dX kernel has
smem headroom the update kernel lacked (update: 4 per-warp tiles + 2×2 frag
grid; dX tiles are only 2KB+2KB), so halving the sync count by processing
**two WMMA K-slices per sync window** should cut the dominant stall without
the occupancy collapse that killed update's kSub=4.

Expected risk (same as update kSub=4): +registers, −occupancy. Update went
45→92 regs / 6→20.5KB smem and died. dX starts at 80 regs / 8KB.

## Implementation

`kernels/packed_ternary/gemm_backward_dx_tc.cu`:
- `kK2 = 2*kWMMA_K = 32`; outer loop steps `r0 += 32`, `tile_r = min(32, N-r0)`.
- Tiles: `dY_smem[64][32]` (4KB), `W_smem[32][64]` (4KB), spill [4][16][16] fp32 (4KB) → 12KB total.
- MMA: 4 frags × 2 K-slices per sync (a_frag ldm=32, `&dY_smem[b_base][ks*16]`; b_frag `&W_smem[ks*16][k_base]`).
- Tail (N not %32): r0 crossing zero-pads via the existing `c < tile_r` guard; only reachable for 16-mult-shapes given the dispatch gate `N_out % 16 == 0`.

## Conclusion

HYPOTHESIS CONFIRMED. Widening the dX K-slice 16→32 held occupancy (5
blocks/SM vs 6–8; smem stayed 12KB) while halving the sync count; isolated
head −6.2%, fc1/fc2 −1.6/−3.3%, and consistent small E2E win (+0.9..1.6%).
Unlike update (where the same idea collapsed at 20.5KB/92regs), dX's larger
tile budget absorbed the change. The update kernel's failure was occupancy,
not the sync structure itself — evidence that dX's 64×64 tile gave enough
room.

**Ship.** Commit `5939fc1`.

## Next recommendation

K64 slice is the obvious follow-up (4 MMAs/sync, 64×32 dY = 8KB + 64×64 W =
8KB → ~20KB smem total, regs likely ~110 → ~4 blocks/SM). Diminishing
returns expected; bench before believing. Beyond that: the per-step sync
chain is now 2 per 32 rows; a real double-buffer (load next tile while MMA
current) is the next structural step, but session 9 showed dX is ~28% of
step time, so K64's ceiling is ~1-2% e2e more.
