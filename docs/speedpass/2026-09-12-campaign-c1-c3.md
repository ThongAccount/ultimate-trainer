## C1. FWD TC64 W_smem row-major — SHIPPED (isolated −38%, e2e confirm)

Commit: `d9ba61f` (kernel) + probe artifacts.

### Hypothesis
The forward kernel stores decoded W into shared memory **transposed**
(`W_smem[k][n]`, k innermost). A lane-level bank-conflict derivation shows every
32-lane W store maps all lanes to **one** 4-byte bank: address
`(c*64 + r)*2` with c = k = inner tid → bank `(c*64+r)/4 % 32` = `(r + 16c... )`
collapses to **32-way conflict**. The proven dX kernel stores W row-major
(`W_smem[n][k]`, inner-stride 1 → ≤2-way). Same trick, one layout.

### Mechanism (why it should win)
Killing a 32-way smem store conflict on every one of the 16 K-slices × 201K CTAs
(head) removes massive store serialization on the forward's hottest instruction.

### Code change
`gemm_forward_tc.cu`:
- `__shared__ half W_smem[kSuperN][kWMMA_K]` (row-major `[n][k]`, was `[kWMMA_K][kSuperN]`)
- W store: `W_smem[r][c]` (r=n outer, c=k inner) — consecutive lanes write consecutive smem
- `b_frag` fragment type: `wmma::col_major` (was row_major), load `&W_smem[n_base][0]`, `ldm=kWMMA_K` (16)
  — the exact pattern the dX kernel uses and is conflict-free with.

Resources unchanged: **88 regs / 20480 B smem / 0 spills**.

### Correctness
In-process parity vs FP32 reference: OLD and NEW errors **identical** on all 3
shapes (fc1 7.8e-3, fc2 3.1e-2, head 1.6e-2). Same numerics, no convergence risk.

### Isolated kernel bench (Modal T4, same-instance interleaved, 3 rounds, min)
| shape | OLD | F1 | Δ |
|---|---|---|---|
| fc1 (1024→4096) | 52.7 ms | 32.2 ms | **−38.8%** |
| fc2 (4096→1024) | 53.2 ms | 32.7 ms | **−38.6%** |
| head (1024→50272) | 653.0 ms | 401.4 ms | **−38.5%** |

Repeat 3-variant probe: OLD 53.3/53.7/658.5, F1 32.1/32.5/405.6 (−39.7/−39.5/−38.4%).

### Step-level profile (F1 tree, full gigatoken, torch.profiler)
`packed_ternary_forward_tc_64_kernel`: **806 ms** (baseline 1371 ms → −41%).
Broken down per step: forward ~806, dX ~965, update ~1112; backward now 70.6% of
the step, forward 26%.

### E2E
First commit-pinned pair (separate Modal instances): baseline 4576.8 ms/step /
3580 tok/s; F1 4755.8 ms/step / 3445 tok/s — contradictory because backward
(unchanged code) drifted +500 ms between instances (Modal T4 noise, thermal).
[TIME] breakdown within each: baseline layers≈718 head≈723 bwd≈3128; F1
layers≈545 head≈549 bwd≈3615 — forward phase consistently −24%, backward
noise-dominated. **Same-instance interleaved e2e (one process, both kernels) is
the decisive measurement**; verdict recorded with it.

### Decision
**KEEP** (pending same-instance e2e confirmation). Forward was the #1 kernel
(1371 ms, ~37%) and this is a pure bank-conflict fix with zero resource/codegen
change and bit-identical numerics.

## C2. FWD K32 on row-major W — FALSIFIED by measurement (K16 wins)

### Hypothesis (backlog A1/B1)
With the transposed-store removed, K-widening (2 WMMA K-slices/sync) might now
win like it did for dX (the E1 +31% loss was attributed to the transpose
scatter, not occupancy).

### Code change
F2 (`tests/fwd_rowmajor_k32.cu`): row-major W tile widened to `[64][32]`,
X to `[64][32]`, outer loop steps 32, 2 MMAs per sync per frag (8 MMAs/sync),
16KB spill retained. 116 regs / 24576 B smem → 2 blocks/SM.

### Isolated bench (same-instance, 3 variants)
| shape | OLD | F1 (K16) | F2 (K32) |
|---|---|---|---|
| fc1 | 53.3 | 32.1 (−39.7%) | 41.8 (−21.7%) |
| fc2 | 53.7 | 32.5 (−39.5%) | 41.9 (−21.9%) |
| head | 658.5 | 405.6 (−38.4%) | 523.6 (−20.5%) |

### Why it lost
Occupancy cliff again: 24 KB smem → 2 blocks/SM (was 3). Even with the store
conflict gone, halving the barrier count buys less than losing a resident
block. **Confirms the K16 row-major layout is the lever; K-widening still loses
on sm_75.** Errors identical to reference (7.8e-3 / 3.1e-2 / 1.6e-2).

### Decision
**REVERT** (variant file only, not production). Documented as negative result:
"fwd K32 loses even with conflict-free W tile at 2 blk/SM; and wins none at K16
headroom." The win ceiling on forward K-slice is already captured by F1.

## C3. UPDATE TC32 kSub=2 batch sub-tiling — FALSIFIED (correct version +43%)

### Hypothesis (backlog A3, the untested middle point)
kSub=4 died earlier at 20 KB/3 blk. kSub=2 (2 batch sub-tiles of 16 per sync)
mirrors the winning dX-K32 resource profile: 12 KB smem, 5 blocks/SM, 20 warps.
Halves the update's 1024-iteration sync chain.

### Code change
`tests/update_ksub2.cu`: `kSub=2`; dY/X smem widened per-warp to 2×16×16;
batch loop steps 32; 2 MMAs per sync; load loops + zero-fill cover both sub-tiles.

### First (buggy) run — warning
Initial version filled only sub-tile 0 → second MMA read **uninitialized smem** →
claimed −23% with WDIFF/CDIFF. **FALSE.** Fixed the load/zero-fill coverage, parity
→ WOK/COK on all shapes.

### Isolated bench (correct version)
| shape | OLD | kSub=2 | Δ |
|---|---|---|---|
| fc1 | 45.40 ms | 65.55 ms | **+44.4%** |
| fc2 | 47.16 ms | 68.13 ms | +44.5% |
| head | 557.8 ms | 800.3 ms | +43.5% |

### Why it lost
74 regs (was 53) + doubled smem holding → effective occupancy drop; the extra
MMA per sync does not compensate. Update kernel's per-16-batch sync path at
8 blk/SM/100% occ is a **local optimum**, consistent with the prior campaign's
kSub=4 result and the S8 64×64-neutral finding.

### Decision
**REVERT** (variant file). Negative result recorded: do not revisit update
K-widening on T4 without a different mechanism (register/occupancy is the floor,
not sync count).

## C4. UPDATE __syncwarp (warp-private tiles) — FALSIFIED (neutral)

### Hypothesis
Update's batch loop uses block-wide `__syncthreads()` twice per 16-batch
iteration, but every smem tile (DYS/XS) and all WMMA fragments are **warp-private**
(indexed by warp_id), and dW accumulation is per-warp. Warps convoy at a block
barrier with no shared data → `__syncwarp()` should let them run fully
independent.

### Code change
`tests/update_syncwarp.cu`: batch-loop barriers (2 of 5) → `__syncwarp()`;
store + partial-batch zero-fill barriers keep `__syncthreads()`.

Resources **identical** to baseline: 53 regs / 8 KB / 0 spills.

### Isolated bench (Modal T4, same-instance, parity WOK COK)
| shape | OLD | syncwarp | Δ |
|---|---|---|---|
| fc1 | 44.34 | 43.35 | −2.2% |
| fc2 | 45.69 | 46.29 | +1.3% |
| head | 546.47 | 535.13 | −2.1% |

All within run-to-run noise (σ ≈ 1-2%). No meaningful change.

### Why it lost
Kernel is not barrier/convoy-bound at 100% occupancy — it's latency-bound on the
per-16-batch load→MMA chain. Removing block barriers without moving the load
pipeline gains nothing.

### Decision
**REVERT** (variant only). Update's sync structure is a local optimum. Combined
with kSub=2 (+43%) and S8 64×64 (neutral), the update kernel is now well-covered:
no tile, occupancy, or sync-tightening change helps on T4.

## C5. FWD half2 vectorized loads — FALSIFIED (neutral vs F1)

### Hypothesis (S5 pattern on update: −7..18%)
F1's row-major store is already conflict-free; but vectorizing W/X loads to
half2 (32-bit ops) could cut instruction count / smem transactions further.

### Code change
`tests/fwd_vec_half2.cu`: W and X cooperative loads rewritten as half2 pairs
(512 pairs, 2 decoded halves per 32-bit store). 90 regs / 20 KB / 0 spills
(+2 regs, same occupancy).

### Isolated bench (Modal T4, same-instance, 3 variants incl. OLD)
| shape | OLD | F1 | C5_vec |
|---|---|---|---|
| fc1 | 52.55 | 32.51 | 32.65 (−37.9%) |
| fc2 | 53.06 | 32.76 | 32.08 (−39.5%) |
| head | 651.17 | 408.80 | 415.46 (−36.2%) |

Errors identical (7.8e-3 / 3.1e-2 / 1.6e-2). C5_vec ≈ F1 within noise.

### Why it lost
F1's scalar row-major store already achieves conflict-free, and the load path is
not transaction-bound — the kernel is latency-bound on the K-loop. Vectorizing
the (already coalesced) load doesn't move the bottleneck.

### Decision
**REVERT** (variant only). F1 remains the forward layout.
